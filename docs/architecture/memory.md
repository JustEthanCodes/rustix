# Memory-management direction

## What exists now

`src/memory.rs` contains an allocation-free `MemoryMapBuilder` that copies Limine ranges into validated half-open physical regions. It rejects empty ranges, `base + length` overflow, overlapping ranges, empty maps, and maps exceeding the fixed 256-region capacity. Known Limine types remain distinct, and unknown type values are preserved. Host-side tests cover range validation/classification, canonical-address boundaries, physical-width bounds, HHDM range arithmetic, and page-rounded ACPI span authorization. `MemoryMap::validate_acpi_span` accepts at most 64 KiB of requested ACPI bytes and validates the entire 4 KiB-rounded physical extent against contiguous ACPI-reclaimable/NVS regions; this is metadata only, not a mapping or dereference grant. `src/boot.rs` stores the resulting map in an owned boot snapshot and reports usable bytes.

`src/frame.rs` provides a fixed-capacity allocator core with host-side tests. It only manages complete 4 KiB frames inside validated `Usable` regions, reserves the first MiB, and coalesces adjacent free ranges. The ownership contract assumes one allocator instance per physical map: within that instance, each eligible frame is owned either by its free-range table or by a non-copyable `Frame` token while allocated. The public constructor does not enforce unique instances, so callers must not initialize multiple allocators for the same physical map; the boot path retains one allocator in `BootInfo`. `allocate` returns `None` when no free frame remains. `deallocate` consumes the token only on success; on any error, including free-range-table exhaustion, it returns a `DeallocationError` containing the original token and leaves allocator state unchanged. The range tables each have a fixed `MAX_FRAME_RANGES` capacity, so fragmentation can prevent a frame from being returned until nearby ranges coalesce. The active cloned page-table hierarchy owns its page-table frames; the frame allocator is otherwise not yet a general-purpose virtual-memory service.

`Frame::address()` is a physical address value, not a dereferenceable pointer and not a proof that the frame is mapped. CPU diagnostics now read `CR4.LA57` to report the active linear-address width (48 or 57 bits) and query `CPUID.80000008H` for physical and maximum linear-address widths when available. Boot-protocol pointers are checked against the active width, with host tests for 48- and 57-bit canonical boundaries. These facts do not prove that any physical address is mapped.

`src/paging.rs` contains host-tested mapping and cache policy plus a bounded candidate-root builder. The CR3 decoder validates physical-address width and reserved bits and interprets its low 12 bits according to active `CR4.PCIDE`; it does not dereference the root. The mapping-range validator requires known physical width, checked aligned bounds, canonical virtual endpoints in one canonical half, and rejects writable-executable permissions. It can encode one 4 KiB leaf PTE with supervisor/user and write permissions, NX when EFER.NXE is confirmed, and a bounded PAT index. `PatLayout` parses supplied `IA32_PAT` values and selects WB, UC, or WC indexes. `MtrrMemoryType`, `VariableMtrr`, `FixedMtrrRanges`, and `MtrrLayout` resolve address-specific MTRR types, including fixed-range priority and defined variable-overlap rules; undefined overlaps fail closed. `MtrrRegisters::validated_layout` validates captured capability/default-type bits, register counts and fixed-range presence, WC support, and variable-mask shape/alignment before producing an owned layout. Rustix supports contiguous power-of-two variable masks and explicitly rejects unsupported discontinuous masks. The layout combines address-specific MTRR type and PAT selection according to Intel SDM Table 11-7 only when `CR0.CD` and `CR0.NW` are clear. Host tests cover all 30 documented MTRR/PAT pairs and malformed inputs. A pure range selector chooses an index only when its effective type is uniform throughout all fixed/variable MTRR boundaries in an aligned extent; selected attributes remain bound to that physical extent. The selector itself does not inspect PTEs, aliases, or frame ownership. Boot reads CR0 without modifying it, validates captured MTRR/PAT state, and reports a diagnostic PA 0 resolution; this does not assert the live PTE's type. MTRR capture is bounded to 32 variable pairs and rejects excess capacity without partial state.

`CandidatePageTables` owns a separate root, bounded to 32 table frames and 256 explicitly mapped leaf records. Ordinary owned leaves require allocator-issued `Frame` tokens; a separate bounded ACPI path accepts only one read-only, supervisor, NX 4 KiB page contained in a `ValidatedAcpiSpan` and never transfers ownership of that physical page. Both paths require NXE, support four- and five-level paths, and hold one exclusive mutable borrow of the unsafe memory backend so prepared handles cannot be mixed across backends. Borrowed ACPI mappings can only be installed and removed while the candidate is inactive. The boot-only ACPI reader performs temporary CR3 switches to read validated pages and removes them before permanent activation. The default boot path clones the complete reachable Limine hierarchy, hardens kernel HHDM aliases to text/rodata R/NX and data RW/NX while preserving PAT bits, verifies critical translations, activates the cloned CR3, and retains the candidate tokens for the active root's lifetime. The CR3 transition invalidates the active PCID and toggles CR4.PGE when enabled; the same invalidation is used if verification restores the inherited root. General candidate mutation and release are rejected while active, but narrow owned-page active map/unmap operations are supported under the single-CPU, IF-disabled contract and invalidate the local TLB before ownership is returned. Host tests cover transactional rollback and ownership; `just active-map-smoke` validates active mapping, access, invalidation, and reclamation in QEMU. The type never writes CR3. The HHDM adapter derives table pointers only from complete allocator-owned `Usable` frames through checked arithmetic.

The opt-in `just frame-smoke` probe reads the inherited root and follows paths for every page in kernel text/rodata/data and the requested stack span. The transition clones every reachable present table and preserves leaf mappings, then rewrites and validates the kernel-image HHDM aliases. The kernel and HHDM aliases retain the same PAT index; MTRR state is unchanged. This is not a fresh address-space policy or a hardware-level exhaustive inventory, and it does not reclaim the inherited root or bootloader memory.

The effective-type resolver follows [Intel SDM Vol. 3A §11.5.2.2, Table 11-7](https://cdrdv2-public.intel.com/671447/325384-sdm-vol-3abcd.pdf), which applies when normal caching is enabled (`CR0.CD=0`, `CR0.NW=0`). Its footnotes distinguish UC selected by an MTRR from UC selected by a page-table entry (the latter involves cache snooping and aliasing concerns); they also identify combinations that older manual editions called undefined but current processors supporting both PAT and MTRRs resolve as shown. The resolver does not cover legacy PCD/PWT-only selection or model-specific combinations outside that table.

The requested Limine base revision is 3. Its protocol maps only `Usable`, `BootloaderReclaimable`, `ExecutableAndModules`, and `Framebuffer` memory-map regions into the HHDM; reserved, ACPI, bad, and unknown regions are not in that mapping set. HHDM mappings use at least 4 KiB granularity and may cover page-aligned bytes beyond unaligned region boundaries. Limine's inherited HHDM mappings are supervisor RWX, normally write-back cached, with framebuffer mappings write-combining when PAT is available. Before activating the cloned root, Rustix splits inherited huge pages where needed and changes the kernel image HHDM aliases to the matching R/NX or RW/NX policy while retaining PAT bits. The rest of the HHDM remains inherited; an HHDM offset is not a blanket physical-memory access grant. See the [Limine base revision 3 protocol](https://github.com/limine-bootloader/limine-protocol/blob/trunk/PROTOCOL.md#base-revision-3) and its memory-layout/caching sections.

The boot snapshot rejects physical map ranges beyond the reported CPUID physical-address width when available. For base-revision-3 HHDM-mapped types it validates page-rounded physical spans, checked `offset + address` arithmetic, and canonical endpoints in the active linear-address width. These checks are metadata, not proof that loader pointers are readable. Arbitrary physical access is not permitted: validated ACPI pages use the bounded read-only/NX reader; HHDM table access is limited to checked full-frame paths. Rustix-owned mappings should be non-executable by default; MMIO requires an explicit device range and cache policy, and guard regions must remain unmapped. The active clone owns its page-table frames but leaves inherited leaf frames and the old root unreclaimed. The global heap begins with a 256 KiB BSS arena and can demand-map up to 1 MiB of allocator-backed pages in its reserved virtual range. Its IRQ-save lock prevents local interrupt reentrancy, but allocation remains forbidden in IRQ/exception handlers. Bootstrap exceptions remain fatal, while selected maskable IRQs are enabled only after APIC routes and handlers are ready.

## Active-root preservation and remaining limits

The transition clones the complete reachable inherited hierarchy rather than building a clean address space. It preserves all reachable present leaves and non-present entries, owns each cloned intermediate table, and fails closed on malformed entries, unsupported page sizes, cross-level table aliases, or fixed-capacity exhaustion. Kernel text/rodata/data HHDM aliases are then adjusted to avoid writable-executable aliases. Limine's original root and leaf frames remain intact.

- **Kernel ELF image:** `linker.ld` places `.text`, `.rodata`, `.limine_requests`, `.data`, `.bss`, and `.got` in three `PT_LOAD` segments: RX text, read-only rodata, and RW data/BSS. It exports `__kernel_start` and `__kernel_end` around the complete loadable image, plus page-aligned bounds for each segment. `BootInfo` checks that Limine's reported virtual base matches the linker start, validates ordered contiguous segment bounds covering the rounded image, derives corresponding half-open physical ranges from the executable physical base with checked arithmetic, and validates canonical virtual and reported physical address widths. The release ELF and QEMU runtime report both showed the three aligned ranges on 2026-10-21. The RX, R/NX, and RW/NX labels describe the linker segment intent; these are linker/boot metadata, not proof that the inherited page tables map every page or enforce those permissions, nor proof that loader pointers are readable. The memory-map `ExecutableAndModules` entries remain illustrative, not an authoritative kernel-image extent.
- **Active stack and `BootInfo`:** The assembly `_start` shim captures Limine's entry `RSP` before any Rust prologue. Under the SysV entry convention the synthetic return slot occupies 8 bytes, so `RSP + 8` is the exclusive stack top. Rustix requests a 256 KiB Limine stack and requires the stack-size response; `BootInfo` records and validates that requested span through the HHDM, including its `BootloaderReclaimable` backing. The loader may allocate more, and no guard page is inferred. QEMU transition tests walk all 64 requested stack pages.
- **Kernel static data:** `RAM_FILESYSTEM`, GDT, IDT, TSS, the ring-0 stack, and double-fault IST stack are static BSS/data in the kernel image. Exception entry also requires the handler code and the TSS/IDT references to remain mapped. Preserve the complete relevant data/BSS pages and stack pages.
- **Limine request data:** request records are in the kernel's writable `.limine_requests` segment. Response objects and the memory-map pointer array are bootloader-reclaimable; `capture_boot_information` copies the values used later, and the shell does not retain those pointers. Keep them mapped until the copy and validation finish; any later reclaim must be explicit rather than reclaiming the whole bootloader-reclaimable class.
- **Inherited page tables:** Limine places its page tables in bootloader-reclaimable memory, but their layout is unspecified. `BootInfo` captures raw CR3 and validates the decoded root address and active low-bit mode. The default boot path clones all reachable page-table pages into allocator-owned frames and preserves all leaf entries, then changes only the kernel-image HHDM alias permission bits while retaining cache attributes. It verifies kernel segments, the requested stack span, and the candidate-root HHDM alias before switching; afterward it verifies CR3 and the critical paths again. The inherited root and its backing pages remain untouched and are not reclaimed.
- **Devices:** COM1 uses x86 port I/O and needs no MMIO virtual mapping. Rustix does not currently request or use a framebuffer. Any future framebuffer or device-register mapping needs an explicit physical range and cache policy.

## Permissions and cache policy of the active clone

The active root preserves Limine's inherited kernel virtual mappings and their cache attributes. Before switching, Rustix requires NXE and enforces the linker permissions for every kernel-image HHDM alias: text and rodata are read-only/NX, and data/BSS/GOT are RW/NX. This prevents writable-executable aliases without discarding the HHDM alias. Huge-page leaves are split as necessary; unaffected entries retain their mappings and PAT/MTRR effective types. The remainder of the HHDM and all non-kernel aliases remain as Limine supplied them, so this is not yet a comprehensive Rustix mapping policy.

Preserve the inherited PAT/MTRR configuration during the first transition. The boot report validates captured registers and computes a diagnostic effective type from the active PAT/MTRR values under normal caching. A separate pure selector can choose an index whose effective type remains uniform across an aligned physical range; the selector itself does not inspect PTEs or aliases. The opt-in `just frame-smoke` probe now compares effective types of the inherited kernel and HHDM aliases for kernel-image pages, but it is not a full alias inventory. The pure combination follows Intel SDM Table 11-7; it is not a generic rule for legacy PCD/PWT-only selection or model-specific combinations. The active transition retains the inherited PAT and MTRR state and changes no cache-selection bits. The page-table split copies large-page PAT selection to the equivalent 4 KiB/2 MiB entries. Future MMIO mappings must still use explicit device ranges and a verified cache policy; do not infer MMIO from generic reserved memory-map entries. COM1 uses port I/O and requires no MMIO mapping.

Do not use huge pages in the first root; add them only when physical coverage, permissions, and cache attributes are uniform across the entire huge-page extent. Future Rustix-owned downward-growing stacks should have at least one 4 KiB unmapped guard page below them. The Limine bootstrap stack has no known guard, so none may be assumed there.

Never modify Limine's active page tables in place. `src/paging.rs` builds an owned clone in allocator-issued frames, can split inherited large pages to update leaf permissions, and supports transactional 4 KiB map/unmap operations before activation. The default boot path validates critical translations and kernel alias permissions, switches CR3 while invalidating stale global translations via a CR4.PGE toggle when needed, verifies the active root, and retains its frame tokens for the active lifetime. The inherited root and backing memory remain intact. This preserves inherited mappings rather than constructing a new address space; broader mapping inventory, non-kernel permission policy, reclamation, and a general mapping service remain future work.

## Planned memory layers

1. **Validated physical regions:** implemented as a fixed-capacity owned snapshot; allocator ownership and reclaim policy remain future work.
2. **Frame allocator integration:** the bounded core is initialized from `BootInfo`; table and leaf mappings use allocator-issued tokens. The active mapping smoke validates one owned page's map/access/unmap/reclamation path.
3. **Kernel virtual memory:** Rustix runs on an active clone of Limine's hierarchy and hardens kernel-image HHDM aliases. Narrow active owned-page map/unmap operations invalidate the local TLB; this is not a clean-room address-space policy or general MMIO subsystem.
4. **Heap:** a 256 KiB BSS arena with 128 allocation records is backed by a bounded, demand-mapped extension of up to 1 MiB. Host tests and QEMU cover growth, reuse, exhaustion, and failed growth. The global allocator uses an IRQ-save spin lock, but allocation remains prohibited in interrupt context so handlers stay bounded and allocation-free.
5. **Process address spaces:** isolate userspace; define copy-in/copy-out helpers and never treat user pointers as kernel references.

## Invariants to preserve

- Physical ranges use checked arithmetic and the half-open convention `[start, end)`.
- Only complete frames in validated `Usable` regions enter the allocator; the first MiB remains reserved. Firmware and loader-reclaimable regions are not silently promoted to free memory.
- Under the single-allocator-per-physical-map contract, a frame is represented by one allocator-free range or one caller-owned, non-copyable `Frame` token. Only a successful `deallocate` transfers the token back to the allocator; errors return the token and leave allocator ranges and accounting unchanged. The current public constructor relies on callers to enforce unique allocator instances.
- `allocate` returns `None` on frame exhaustion. Metadata-capacity exhaustion is an explicit error, never silent loss of a frame.
- A `Frame` address is physical, not directly dereferenceable. HHDM translation and table access are limited to checked full-frame token-based paths that rely on Limine's documented mapping contract. Candidate mutations are allowed only before activation and only in owned tables. The active cloned root retains its ownership tokens and rejects mutation/release until an explicit, reviewed CR3 transition away from it.
- Mapping changes validate alignment, canonical addresses, ownership, and permissions before touching tables.
- User-controlled addresses are validated on every syscall boundary; prior validation is not a substitute for access checks during later copies.
- Tests cover unaligned edges, exact-boundary allocations, arithmetic overflow, overlaps, exhaustion, and unchanged state/ownership on failure.

The active root is a full clone of Limine's reachable hierarchy with kernel HHDM alias W^X hardening, not a clean-room Rustix address space. Heap growth is bounded to a fixed virtual reservation and 1 MiB of frame-backed pages. Broader alias/MMIO coverage, frame reclamation, and physical-hardware validation remain outstanding.
