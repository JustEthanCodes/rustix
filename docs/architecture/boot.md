# Boot protocol and kernel entry

## Current boot contract

Rustix currently expects a Limine-compatible x86_64 handoff. Limine is an external loader; it does not implement Rustix's kernel services. The kernel requests protocol base revision 3, a 256 KiB x86_64 stack, the higher-half direct-map (HHDM) offset, the executable physical/virtual base addresses, the memory map, and the ACPI RSDP. Before using any base-revision-3 guarantees, boot volatile-reads the loader-updated base-revision field and accepts only the protocol's supported marker value `0`; a nonzero value means revision 3 was not honored.

Requests are kept in `.limine_requests_start`, `.limine_requests`, and `.limine_requests_end` by `linker.ld`. The response-bearing request records are mutable and the output `.limine_requests` section is placed in a writable load segment because Limine fills their response pointers before entering Rustix. The ELF entry symbol is `_start`.

### Entry sequence

1. Limine loads the ELF and transfers control to the assembly `_start` shim under the x86_64 Limine protocol. The shim captures the entry `RSP`, aligns the stack for a SysV call, and invokes `rustix_start`.
2. `rustix_start` configures the legacy COM1 UART for polling output and input.
3. The kernel disables maskable interrupts and installs its bootstrap GDT, TSS, and fatal-exception IDT. This does not initialize IRQ delivery.
4. Before relying on Limine base-revision-3 semantics, the kernel volatile-reads the loader-updated request field and requires its supported marker to be `0` (unsupported loaders leave the requested value nonzero). It then reads CR0 caching-control state, CPU address widths, active `CR4.PCIDE`, and raw CR3. It decodes CR3's physical root address and low-bit meaning against those CPU properties, without dereferencing the root. It reads EFER.NXE only when CPUID reports NX, `IA32_PAT` only when CPUID reports PAT, and MTRR registers only when CPUID reports MTRR support; these reads do not change CPU state. The MTRR snapshot is bounded to 32 variable pairs and reports an explicit capacity-exceeded state without retaining partial registers. It requires and validates the stack-size response, copies the HHDM, executable-address, and memory-map responses into an owned `BootInfo` snapshot, validates pointers against the active linear width, derives and validates the linker-defined kernel image span and its page-aligned text/rodata/data segment spans from Limine's executable bases, and derives the requested 256 KiB initial-stack span from the captured entry `RSP`. If the optional RSDP response is present, it treats its address as physical under validated base revision 3 and validates the initial 20-byte span and its complete page-rounded mapping extent against ACPI-reclaimable/NVS map regions and the known physical width. Before the permanent CR3 switch, a temporary reader maps validated ACPI pages read-only/NX in the candidate root, reads and validates RSDP → RSDT/XSDT → MADT, copies the parsed MADT into `BootInfo`, and removes each borrowed mapping after restoring the prior CR3. It validates physical bounds, stack HHDM arithmetic/coverage, and page-rounded HHDM arithmetic for protocol-mapped memory types. It then builds a frame allocator only from validated usable ranges and rejects malformed metadata before starting the shell.
5. The kernel reports raw CR3 and its decoded physical root/low bits when the reported width permits, physical and virtual kernel-image spans, linker-defined segment permissions, the requested stack span, validated memory ranges, frame counts, CPU features/address widths, NXE and normal-caching state, the active PAT value plus recognized WB/UC/WC indices, and a summary of captured MTRR state. It also reports a diagnostic effective type at physical address zero for PAT index 0; this is not a live mapping claim.
6. Before entering the shell, the kernel clones the reachable inherited hierarchy into allocator-owned frames, makes the kernel-image HHDM aliases R/NX or RW/NX while preserving PAT bits, verifies critical mappings, temporarily switches to the candidate to copy validated ACPI MADT data when available, then performs the permanent CR3 switch and verifies the active root. It retains ownership tokens for the lifetime of the active root and probes the fixed heap.
7. The kernel seeds a volatile RAM filesystem and enters Crabshell. The shell busy-polls COM1 because no scheduler or UART interrupt handler exists; the kernel does not return to the loader.

The linker exports page-aligned virtual bounds for each of the kernel's three load segments. Boot validates their order, contiguity, coverage of the rounded image span, and derived physical ranges, then reports the permissions intended by `linker.ld`. Boot also decodes CR3's root physical address and active low-bit interpretation. The opt-in `just frame-smoke` path reads the 512 root entries and follows every page in the kernel image segments and requested stack span. The default boot transition clones the complete reachable table graph, applies and checks kernel HHDM alias permissions while preserving PAT bits, and verifies the candidate and active critical paths. This is a clone of Limine's mapping graph, not a clean-room mapping policy or exhaustive validation of unrelated aliases.

The memory-map snapshot stores physical regions as checked half-open ranges `[start, end)` and retains Limine's known classifications plus unknown type values. It does not authorize Rustix to access every region or reclaim loader memory. Rustix checks physical bounds and calculates canonical HHDM ranges for memory types covered by the requested base revision. The active cloned root leaves the inherited root and loader-owned leaf frames untouched. The opt-in `just frame-smoke` probe writes one allocator-issued frame contained in a validated `Usable` region and reads the inherited root page after checking that it is bootloader-reclaimable; both accesses rely on the Limine mapping contract after checked address arithmetic. It does not prove full live page-table coverage. These metadata checks cannot prove that a Limine-provided non-null pointer is readable; that remains an explicit trust assumption of the Limine handoff.

## Link and target configuration

- Rust target: `x86_64-unknown-none`
- Linker script: `linker.ld`
- Kernel virtual base: `0xffffffff80000000`
- Required code-generation constraints: kernel code model, static relocation, and disabled red zone
- Rust panic strategy: abort; the panic handler logs and halts

See [`../development/building.md`](../development/building.md) for commands and toolchain setup.

## Failure behavior and limitations

An unsupported Limine base revision, missing required responses (including the stack-size response), bad pointers/alignment, invalid HHDM values, invalid image or segment bounds, invalid requested-stack spans, excessive counts, null entries, address arithmetic overflow, and invalid or overlapping physical ranges reject the complete boot snapshot. If an RSDP response is present but has a null address or its initial page-rounded mapping extent is not fully covered by validated ACPI regions, the complete snapshot is rejected; no RSDP response is allowed and reported as ACPI unavailable. Later ACPI table-read or cache-policy failures are reported as MADT unavailable and do not enable interrupts. `_start` halts before starting Crabshell rather than continuing with partial memory metadata. Structural checks cannot establish that a non-null loader pointer is mapped and readable; that remains an explicit trust assumption of the Limine handoff. The installed exception handlers print fatal context and halt; no fault recovery or maskable IRQ delivery is provided. COM1 writes use a bounded polling loop so a non-responsive UART does not block forever.

The repository includes a Limine v12.9.3 binary archive pin with SHA-256 verification, a hybrid ISO recipe, and a bounded QEMU serial smoke test that checks Crabshell's prompt. On 2026-10-16, `just verify` passed in WSL2 Ubuntu 24.04 on both the working tree and a clean detached worktree with an empty `target` directory; the clean run fetched and built the pinned Limine host utility, created the image, and QEMU reported boot metadata before reaching the prompt. Milestone 0's local exit criteria are met. Hosted CI has not been observed. There is still no framebuffer console, reboot/shutdown interface, or broader boot-protocol compatibility test. The available serial and keyboard drivers do not imply a general device model.

## Future boot work

The kernel snapshots and validates the Limine map and preserves firmware and loader-reclaimable classifications without reclaiming them. The frame allocator manages only validated `Usable` regions; cloned page-table frames are retained as owned tokens. Loader-reclaimable memory remains unavailable until Rustix has copied any needed boot data and explicitly reaches a documented reclaim point; ACPI reclaimable memory needs the ACPI tables to be copied or parsed first.
